# Why generated tests fail, and when they improve the test suite

This note covers Sections V.A and V.B of the paper for PDFBox, and the "prediction check" of the plan: can the
final Descartes status of each target be predicted from the values its tests observed in production? All results
are computed for both test sets: the authors' published tests and the tests generated by this reproduction, with
the verdicts of the five runs of [execution.md](execution.md) and the "after" Descartes runs of
[descartes.md](descartes.md).

| Script | Output |
|---|---|
| `analysis/generated_tests.py` | reads the oracle of each generated test (the value observed in production) |
| `analysis/failure_analysis.py` | `results/day8/failure_analysis_{reproduction,authors}.*` |
| `analysis/prediction_check.py` | `results/day8/prediction_check_{reproduction,authors}.*` |
| `analysis/java/CacheLookupCheck.java` | `results/day8/cache_lookup_check.txt` |

## The oracle

pankti-generate ends every test with one assertion on the value the method returned in production:

```java
Assert.assertEquals(32, receivingObject.getFlags());                         // primitive or null: a literal
Assert.assertEquals(expectedObject, receivingObject.getPath(79));            // object deserialised by XStream
Assert.assertTrue(Arrays.equals(expectedObject, receivingObject.readUnsignedByteArray(77)));   // array
```

`assertEquals` calls `equals()`. For a class that does not override it, two distinct objects are never equal, even
when all their fields are the same.

## Section V.A: why tests fail

The paper analyses "a random sample" by hand. Here every failing test is classified, from its JUnit message
(`expected:<...> but was:<...>`) and its observed value:

| | Methods with failing tests | Failing tests | equals by identity | returns null | exception |
|---|---|---|---|---|---|
| Authors' tests | 13 | 237 | 151 | 86 | 0 |
| Reproduction's tests | 14 | 365 | 265 | 98 | 2 |

**In every one of these methods, a test passes exactly when the value observed in production was `null`**: the
passing tests all observed `null` (128 for the authors' tests, 117 here), and none of the failing tests did. Every
failing method returns an object; no test of a method returning a primitive, a wrapper, a string, an enum or an
array fails, as the paper reports.

Two mechanisms explain all the failures:

1. **The returned class compares by identity.** `GeneralPath` (JDK), `PDEncryption`, `PDExtendedGraphicsState`,
   `PDViewerPreferences`, `PDCIDSystemInfo` and `OS2WindowsMetricsTable` do not override `equals()` in PDFBox 2.0.21
   (checked in the sources). A deserialised expected object can therefore never equal the object the method returns,
   whatever their content. The messages show it: `expected:<java.awt.geom.GeneralPath@54e81b21> but
   was:<java.awt.geom.GeneralPath@38d5b107>`, or, for `PDCIDSystemInfo`, which overrides `toString()` only, two
   identical texts (`Adobe-Identity-0`).
2. **The lookup returns null.** `DefaultResourceCache.get*(COSObject)` and `FontCache.getFont(FontInfo)` read a
   `Map` whose keys are `COSObject` or `FontInfo`. Neither class overrides `equals()` or `hashCode()`, so the map
   finds a key only if it is the very same instance. In a test, the receiving object (with its cache) and the
   parameter are deserialised from two separate XML files, so the parameter is a different instance from the key
   and the method returns `null`.

   A run-time check confirms it (`analysis/java/CacheLookupCheck.java`, on three failing tests of the authors,
   `results/day8/cache_lookup_check.txt`). The deserialised cache is complete: 3, 4 and 7 entries, each
   `SoftReference` still pointing to its object. The parameter is not a key, so the call returns `null`. Called with
   the cache's own key that has the same object number, the method returns the expected object, e.g.
   `PDTrueTypeFont BJEDFM+ArialMT`. Even then the assertion would most likely still fail, by mechanism 1 (`PDFont.equals`
   compares the underlying PDF dictionaries by identity; `PDColorSpace` and `PDXObject` do not override `equals`).
   This last point is read from the code, not run.

The `getOS2Windows` tests (a target of this reproduction only) fail by mechanism 1, plus 2 tests with an
`IOException` ("Bad file descriptor"): the receiving `TrueTypeFont` reads its tables lazily from a file that was
open in production and cannot be reopened from a profile.

### Comparison with the paper's causes

| Rows of Table III | Paper | Observed here |
|---|---|---|
| 51, 72, 73 | `equals` not overridden | confirmed (mechanism 1) |
| 37, 44, 45, 46, 50 | in-memory caches based on `SoftReference` "not available in the testing environment" | the cache *is* restored with its content; the lookup fails because its keys compare by identity (mechanism 2) |
| 33, 34, 35, 53, 73 | returned objects with transient fields (`GeneralPath`, `IdentityHashMap`) | the returned classes (`GeneralPath`, `PDEncryption`) do not override `equals`, so the assertion fails for any two distinct objects (mechanism 1); transient fields cannot be the deciding cause. `GeneralPath` is serialised through its custom `writeObject`, which writes its coordinates (`serialization="custom"` in the XML) |
| 74 (`getCIDSystemInfo`, 1 failing test) | not explained | mechanism 1 |
| - | custom serialisation (Broadleaf only) | no PDFBox case |

The paper's diagnosis and this one agree on the outcome (these tests fail in any environment) and differ on the
mechanism for 9 of the 12 rows the paper lists (33, 34, 35, 37, 44, 45, 46, 50, 53). For the transient-field rows, this analysis shows that `equals` suffices to make
the tests fail; it does not show whether the transient fields would also differ under a deep comparison (not
tested).

## Section V.B: passing tests that do not improve the test suite

The paper reports 15 targets (12 in PDFBox) that have passing tests but stay pseudo-tested, because their tests only
observed `null` and Descartes applies a single mutant to them, `return null;`. With both test sets, exactly **12
PDFBox targets** are in this case (rows 37, 44, 45, 46, 48, 50, 53, 55, 56, 58, 66, 72). For each of them, all
passing tests observed `null`, and Descartes created only the `null` mutant. The paper's explanation is confirmed
exactly.

## Prediction check

A passing test that asserts the observed value with `equals` kills every extreme mutant whose default value
differs from that value. This rule (`generated_tests.mutant_killed`) predicts each mutant of each target from the
values observed by the target's own passing tests:

| | Mutants predicted correctly | Targets with the predicted classification |
|---|---|---|
| Authors' tests | 82 / 82 | 47 / 47 |
| Reproduction's tests | 82 / 82 | 47 / 47 |

So no mutant that the target's own tests leave alive is killed by another test (an existing PDFBox test or a
generated test of another target). `isFill` is the typical case. Its only observed value is `true`, so the test kills
the `false` mutant and not the `true` mutant: partially tested.

## What decides the final status

Classified by return type (`results/day8/prediction_check_*.txt`), the 47 targets split exactly:

| Return type | Targets | Well-tested after |
|---|---|---|
| primitive | 17 | 17 |
| `String` or wrapper | 8 | 8 |
| array of primitives | 2 | 2 |
| enum | 1 | 1 |
| other object | 19 | 0 |

Of the 19 targets that return another object, 14 return a PDFBox class that does not declare `equals`, 4 a
`GeneralPath` (JDK) and 1 a `PDFont`, whose `equals` compares the underlying PDF dictionary by identity. For such a target, a test with a non-null
observed value fails, so the only passing tests are the null-only ones, and those cannot kill the `null` mutant.
In this case study, PANKTI's assertion strategy can therefore improve a target only if it returns a value type; the
28 / 46 of the paper follows from the return types of the 46 targets and the values observed for them.

## Limitations

- The classification uses the failure messages and the source code; the run-time check covers mechanism 2 on three
  tests of the authors. A deep comparison of the objects (field by field) was not done, so whether transient fields
  would also differ is not known.
- The prediction rule assumes that a test reaches the mutated method and compares with `equals`; it was
  checked against the actual Descartes results, not proved.
